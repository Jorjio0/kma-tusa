## Про проєкт

Студенти Могилянки постійно влаштовують вечірки, квартирники, (колись повернеться) «Бунтівник» та інші зібрання, щоб відпочити після пар. Але дізнатися про них можна лише випадково: з історії в Instagram, з репосту в Telegram-чаті або від друга, який «чув, що в суботу щось буде». Організаторам, своєю чергою, складно зібрати людей і порахувати, скільки їх прийде.

**KMA Tusa** це одне місце для всіх студентських тусовок:

- студент бачить **афішу** найближчих тусовок, може знайти потрібну за назвою чи організатором і відфільтрувати за типом (вечірка, квартирник, настолки…), датою, локацією, умовами входу та іншими параметрами;
- на сторінці тусовки є все, що треба знати перед тим, як іти: опис, дата й час, хто грає або виступає (лайнап), дрес-код, умови входу, посилання на збір, організатори і скільки ще залишилося місць;
- більшість тусовок у Могилянці **благодійні** (вхід за донат на збір для ЗСУ чи іншої ініціативи) або **безкоштовні**, а платний квиток трапляється рідше. Тому в кожної тусовки вказано тип входу: *вільний*, *за донат* або *квиток*. Для благодійних тусовок показано мету збору й посилання на банку. Сайт сам гроші не приймає: донат робиться за посиланням на збір;
- можна переглянути **організаторів** і всі їхні тусовки;
- можна переглянути **локації** і всі тусовки, що там проходять;
- зареєстрований користувач додає квитки в **кошик** (наприклад, на кілька тусовок одразу або кілька квитків для друзів) і оформлює **замовлення**. «Квиток» тут означає місце на тусовці, а не обов'язково платний вхід. У першій версії оплати немає: натискання «Оформити» одразу створює замовлення. Безкоштовні та благодійні тусовки теж оформлюються через замовлення, щоб організатор знав, скільки людей прийде;
- у **профілі** користувач бачить історію замовлень (куди він іде і де вже був) та може редагувати дані про себе;
- адміністратор додає, редагує та видаляє тусовки, організаторів, локації й категорії.

## Ролі користувачів

| Роль | Що може |
|---|---|
| Гість | Переглядати афішу, тусовки, організаторів, локації, сторінку «Про нас»; зареєструватися або увійти |
| Користувач | Усе, що гість, а також додавати, редагувати й видаляти тусовки та організаторів; надалі кошик, замовлення, профіль |
| Адміністратор | Усе, що користувач, а також додавати, редагувати й видаляти категорії та локації |

Роль визначається за токеном у запиті: без токена це гість, з токеном користувач, а адміністратор має прапорець `is_staff`. Детально в розділі [Авторизація і права доступу](#авторизація-і-права-доступу).

## Як запустити проєкт

Потрібен Python 3.12, 3.13 або 3.14. Усі команди виконуються в папці, де лежить `manage.py`.

1. Склонуйте репозиторій:

   ```bash
   git clone https://github.com/Jorjio0/kma-tusa.git
   cd kma-tusa
   ```

2. Створіть і активуйте віртуальне середовище:

   ```bash
   python -m venv .venv

   # Windows (PowerShell)
   .venv\Scripts\activate
   # Linux / macOS
   source .venv/bin/activate
   ```

3. Встановіть залежності:

   ```bash
   python -m pip install -r requirements-dev.txt
   ```

   `requirements.txt` містить те, що потрібно серверу (Django, Django REST framework, django-cors-headers, djangorestframework-simplejwt, drf-spectacular, python-decouple), а `requirements-dev.txt` ще й інструменти перевірки коду та тестів (ruff, pytest, pytest-django, pytest-cov).

4. Створіть файл `.env` з налаштуваннями (див. [Змінні середовища](#змінні-середовища)):

   ```bash
   # Windows (PowerShell)
   Copy-Item .env.example .env
   # Linux / macOS
   cp .env.example .env
   ```

   Згенеруйте свій `SECRET_KEY` і вставте його в `.env` замість `change-me-to-a-long-random-string`:

   ```bash
   python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
   ```

5. Створіть базу даних:

   ```bash
   python manage.py migrate
   ```

6. Завантажте демо-дані (6 категорій, 4 організатори, 6 локацій, 8 тусовок) і двох демо-користувачів:

   ```bash
   python manage.py loaddata demo users
   ```

   | Логін | Пароль | Роль |
   |---|---|---|
   | `tusa_admin` | `TusaAdmin2026` | адміністратор |
   | `tusa_student` | `TusaStudent2026` | користувач |

7. Запустіть сервер:

   ```bash
   python manage.py runserver
   ```

   API доступне за адресою **http://127.0.0.1:8000/api/**, наприклад [http://127.0.0.1:8000/api/events/](http://127.0.0.1:8000/api/events/).

8. *(Необов'язково)* Створіть власного адміністратора. Він зможе входити і в API, і в адмінку Django (http://127.0.0.1:8000/admin/):

   ```bash
   python manage.py createsuperuser
   ```

Перевірка стилю коду (PEP 8, форматування) перед комітом:

```bash
python check_submission.py           # перевірити
python check_submission.py --format  # автоматично виправити форматування
```

## Змінні середовища

Секретні й залежні від середовища налаштування не зберігаються в коді: `config/settings.py` читає їх з файлу `.env` через [python-decouple](https://pypi.org/project/python-decouple/). Файл `.env` додано в `.gitignore`, тому він не потрапляє в Git. У репозиторії лежить лише `.env.example` із заглушками.

| Змінна | Обов'язкова | Приклад | Що означає |
|---|:---:|---|---|
| `SECRET_KEY` | так | довгий випадковий рядок | Ключ Django для підписів, зокрема JWT-токенів. Без нього сервер не запуститься |
| `DEBUG` | ні (`False`) | `True` | Режим розробки: детальні сторінки помилок і browsable API |
| `ALLOWED_HOSTS` | ні (`localhost,127.0.0.1`) | `localhost,127.0.0.1` | Хости, з яких Django приймає запити, через кому |
| `CORS_ALLOWED_ORIGINS` | ні (порт 5173) | `http://localhost:5173,http://127.0.0.1:5173` | Адреси фронтенду, яким дозволено звертатися до API з браузера |
| `LOG_LEVEL` | ні (`INFO`) | `DEBUG` | Рівень логування застосунків `events` і `accounts` |

## Тести

Тести написані на **pytest** з плагіном **pytest-django**, запити до API надсилає `APIClient` з Django REST framework. Для тестів створюється окрема тимчасова база, тому робоча `db.sqlite3` не змінюється.

```bash
python -m pip install -r requirements-dev.txt   # якщо ще не встановлено
pytest                                          # запустити всі тести
pytest -v                                       # з назвою кожного тесту
pytest --cov --cov-report=term-missing          # з відсотком покриття
```

Для тестів потрібен файл `.env` (див. [Змінні середовища](#змінні-середовища)).

Що покрито:

- **Тусовки** (`events/tests/test_events_api.py`), усі методи `GET`, `POST`, `PUT`, `DELETE`:
  - позитивні сценарії: список, тусовка за id, створення, оновлення й видалення залогіненим користувачем;
  - негативні сценарії: `401` без токена й з невалідним токеном, `400` для порожнього тіла й порушених бізнес-правил, `404` для неіснуючої тусовки, `405` для `PATCH`.
- **Ролі** (`events/tests/test_roles_api.py`): категорії й локації змінює лише адміністратор (`401` для гостя, `403` для користувача, `201`/`200` для адміністратора), `400` для дубліката назви, `409` при видаленні категорії з тусовками.
- **Авторизація** (`accounts/tests/test_auth_api.py`): реєстрація (пароль зберігається хешем) та її помилки, вхід, неправильний пароль, оновлення токена, `/api/auth/me/`.

Тестові дані готують **фікстури** pytest у `conftest.py` (у корені проєкту): `api_client`, користувачі `user` і `admin_user`, клієнти з токеном `user_client` і `admin_client` (входять через `/api/auth/login/`), об'єкти `category`, `organizer`, `venue`, `event` і тіло запиту `event_data`.

Покриття рахує **pytest-cov** (coverage.py). Налаштування в `.coveragerc`: міграції, самі тести й службові файли не враховуються.

## Документація API (Swagger)

Документація генерується автоматично з коду за стандартом **OpenAPI 3** за допомогою [drf-spectacular](https://drf-spectacular.readthedocs.io/).

- **Swagger UI:** http://127.0.0.1:8000/api/docs/
- **ReDoc:** http://127.0.0.1:8000/api/redoc/
- **OpenAPI-схема (YAML):** http://127.0.0.1:8000/api/schema/, або файлом: `python manage.py spectacular --file schema.yml`

У Swagger UI видно всі ендпоінти, методи, параметри, структуру запитів і відповідей. Ресурс **тусовок** (`/api/events/`) задокументовано детально: опис кожної дії, вимоги до автентифікації, можливі статуси (`200`, `201`, `204`, `400`, `401`, `404`) і приклади запиту та відповідей.

Щоб виконати захищений запит прямо зі Swagger UI:

1. Виконайте `POST /api/auth/login/` (кнопка **Try it out**).
2. Скопіюйте `access` з відповіді.
3. Натисніть **Authorize** угорі сторінки і вставте токен.

## Логування

Логи виводяться в консоль, де запущено сервер, у форматі `час рівень модуль: повідомлення`. Налаштування в `LOGGING` у `config/settings.py`, рівень задає змінна `LOG_LEVEL`.

| Рівень | Що записується |
|---|---|
| `INFO` | Успішні дії: створення, оновлення й видалення записів (id і хто виконав), реєстрація, вхід користувача |
| `WARNING` | Відхилені дії: помилки валідації (лише назви полів, без значень), запис не знайдено, видалення заборонено через пов'язані тусовки (`409`), невдала спроба входу |

Паролі, токени та значення полів у логи не записуються.

Приклад:

```
2026-11-18 07:43:20,575 WARNING accounts.views: Невдала спроба входу для користувача tusa_admin
2026-11-18 07:43:20,585 WARNING events.views: Тусовку id=999 не знайдено
```

## REST API

### Загальні правила

- Усі адреси починаються з `/api/` і **закінчуються слешем**: `/api/events/`, `/api/events/3/`.
- Дані передаються у форматі **JSON** (`Content-Type: application/json`).
- Назви полів у **snake_case** (`starts_at`, `entry_type`), так само як у моделях Django.
- Списки повертаються **простим масивом**, без пагінації, відсортованими: категорії, організатори й локації за назвою, тусовки за часом початку.
- Зв'язки передаються як **id**: `"organizer": 1`, `"venue": 2`, `"category": 3`.
- Методи:

  | Метод | Адреса | Що робить | Успіх |
  |---|---|---|---|
  | `GET` | `/api/<ресурс>/` | список | `200 OK`, масив |
  | `POST` | `/api/<ресурс>/` | створити запис | `201 Created`, створений об'єкт з `id` |
  | `GET` | `/api/<ресурс>/{id}/` | один запис | `200 OK` |
  | `PUT` | `/api/<ресурс>/{id}/` | оновити запис (передаються всі обов'язкові поля) | `200 OK`, оновлений об'єкт |
  | `DELETE` | `/api/<ресурс>/{id}/` | видалити запис | `204 No Content`, тіло порожнє |

- Дата й час у форматі ISO 8601 за київським часом: `"2026-11-14T21:00:00+02:00"`. Можна передавати й без часового поясу (`"2026-11-14T21:00"`), тоді час вважається київським.
- Суми в цілих гривнях, числом: `150`.
- Необов'язкові текстові поля повертаються як порожній рядок `""`, а необов'язкові числа й дати як `null`.
- **Доступ.** Читати (`GET`) можуть усі. Щоб створювати, редагувати й видаляти, потрібен токен у заголовку `Authorization: Bearer <access>`, а для категорій і локацій ще й роль адміністратора. Див. [Авторизація і права доступу](#авторизація-і-права-доступу).

#### Тип входу на тусовку

Кожна тусовка має поле `entry_type`, від якого залежать інші поля:

| `entry_type` | Що означає | `price` | `min_donation` | `fundraising_url` |
|---|---|---|---|---|
| `free` | Вхід вільний | `0` | не вказується | необов'язково (можна задонатити за бажанням) |
| `donation` | Вхід за донат на збір | `0` | мінімальний донат або `null` (будь-який) | **обов'язково** |
| `ticket` | Платний квиток | більше `0` | не вказується | необов'язково (наприклад, частина коштів іде на збір) |

Збір описують поля `fundraising_purpose` (мета), `fundraising_url` (посилання на банку) і `fundraising_goal` (ціль у гривнях, необов'язково). Сайт не приймає гроші: донат робиться за посиланням.

### Формат помилок

Формат однаковий для всіх ендпоінтів (це стандартні формати Django REST framework):

**`400 Bad Request`** — дані не пройшли перевірку. Ключ — назва поля, значення — список повідомлень, щоб фронтенд міг показати їх під потрібним полем форми:

```json
{
  "ends_at": [
    "Час завершення має бути пізніше за час початку."
  ],
  "price": [
    "Ціну вказують лише для платного квитка."
  ],
  "fundraising_url": [
    "Для тусовки за донат вкажіть посилання на збір."
  ],
  "capacity": [
    "Локація вміщує лише 200 людей."
  ]
}
```

**`401`, `403`, `404`, `405`, `409`** — пояснення в полі `detail`:

```json
{
  "detail": "Неможливо видалити категорію Вечірка: у ній є тусовки (3). Спершу перенесіть їх в іншу категорію."
}
```

| Код | Коли повертається |
|---|---|
| `400 Bad Request` | Дані не пройшли перевірку: не заповнені обов'язкові поля, неправильний формат, порушені правила тусовки, тіло не є JSON |
| `401 Unauthorized` | Немає токена, токен невалідний або прострочений; неправильний логін чи пароль при вході |
| `403 Forbidden` | Користувач увійшов, але його ролі не вистачає прав (наприклад, не адміністратор змінює категорію) |
| `404 Not Found` | Запису з таким `id` немає |
| `405 Method Not Allowed` | Ендпоінт не підтримує цей метод (наприклад, `PATCH`) |
| `409 Conflict` | Запис не можна видалити, бо з ним пов'язані тусовки |

**Чому 400, а коли 409.** `400` означає, що неправильні самі дані в запиті: порожня або вже зайнята назва, невідомий тип локації, ціна для безкоштовної тусовки. Їх треба виправити. `409` означає, що запит правильний, але суперечить поточному стану бази: видалити організатора можна, але не поки за ним закріплені тусовки. Якщо спершу видалити чи перенести ці тусовки, той самий запит виконається успішно.

### Обмеження предметної області

| Ситуація | Відповідь |
|---|---|
| Видалення категорії, у якій є тусовки | `409`, у повідомленні кількість тусовок і що зробити |
| Видалення організатора, за яким закріплені тусовки | `409` |
| Видалення локації, у якій заплановані тусовки | `409` |
| Категорія чи організатор з уже зайнятою назвою | `400` |
| Тип входу не відповідає ціні, мінімальному донату чи збору (див. [Тип входу](#тип-входу-на-тусовку)) | `400` |
| Час завершення тусовки раніше за час початку | `400` |
| Місткість тусовки більша за місткість локації | `400` |
| Місткість тусовки чи локації менша за 1 | `400` |

### Авторизація і права доступу

Автентифікація зроблена на **JWT** (JSON Web Token) за допомогою бібліотеки [djangorestframework-simplejwt](https://django-rest-framework-simplejwt.readthedocs.io/). Користувачі зберігаються у вбудованій моделі Django `User` (таблиця `auth_user`), паролі зберігаються лише у вигляді хешу (`pbkdf2_sha256`). Код авторизації лежить в окремому застосунку `accounts`.

#### Як це працює

1. Користувач реєструється: `POST /api/auth/register/`.
2. Користувач входить: `POST /api/auth/login/`. Сервер повертає два токени:
   - **`access`** живе **5 хвилин**. Його надсилають з кожним запитом, якому потрібна авторизація;
   - **`refresh`** живе **1 добу**. Він потрібен лише для того, щоб отримати новий `access`.
3. Клієнт передає `access` у заголовку кожного запиту:

   ```
   Authorization: Bearer <access>
   ```

4. Коли `access` закінчується, сервер відповідає `401`. Клієнт надсилає `refresh` на `POST /api/auth/refresh/`, отримує новий `access` і повторює запит. Користувачу не треба знову вводити пароль.
5. Коли закінчується й `refresh`, користувач входить знову.
6. **Вихід (logout)** відбувається на клієнті: фронтенд видаляє збережені токени. Окремого ендпоінта для виходу немає, бо сервер не зберігає токени: він лише перевіряє їхній підпис і термін дії.

Строки життя токенів задані в `SIMPLE_JWT` у `config/settings.py`.

#### Ролі та права доступу

| Роль | Як визначається | Що може |
|---|---|---|
| Гість | запит без заголовка `Authorization` | читати (`GET`) усі ресурси; зареєструватися й увійти |
| Користувач | будь-який залогінений користувач | усе, що гість, а також створювати, редагувати й видаляти **тусовки** та **організаторів** |
| Адміністратор | користувач з `is_staff = True` (наприклад, створений через `createsuperuser`) | усе, що користувач, а також створювати, редагувати й видаляти **категорії** та **локації** |

| Ресурс | `GET` | `POST`, `PUT`, `DELETE` |
|---|---|---|
| `/api/events/`, `/api/organizers/` | усі | користувач, адміністратор |
| `/api/categories/`, `/api/venues/` | усі | лише адміністратор |
| `/api/auth/register/`, `/api/auth/login/`, `/api/auth/refresh/` | — | усі (`POST`) |
| `/api/auth/me/` | користувач, адміністратор | — |

Права задані атрибутом `permission_classes` у кожному view: вбудований `IsAuthenticatedOrReadOnly` для тусовок і організаторів та власний `IsAdminOrReadOnly` (`accounts/permissions.py`) для категорій і локацій.

**Відповіді без доступу:**

`401 Unauthorized` — токена немає, він невалідний або прострочений. Відповідь містить заголовок `WWW-Authenticate: Bearer realm="api"`:

```json
{
  "detail": "Реквізити перевірки достовірності не надані."
}
```

Для невалідного чи простроченого токена текст повідомлення формує simplejwt (англійською), а поле `code` дорівнює `token_not_valid`. Саме за цим кодом фронтенд розуміє, що треба оновити `access`:

```json
{
  "detail": "Given token not valid for any token type",
  "code": "token_not_valid",
  "messages": [
    {
      "token_class": "AccessToken",
      "token_type": "access",
      "message": "Token is invalid"
    }
  ]
}
```

`403 Forbidden` — користувач увійшов, але його ролі не вистачає прав, наприклад звичайний користувач створює категорію:

```json
{
  "detail": "Цю дію може виконати лише адміністратор."
}
```

**401 чи 403.** `401` означає, що сервер не знає, хто робить запит: треба увійти або оновити токен. `403` означає, що сервер знає користувача, але йому ця дія заборонена: повторний вхід не допоможе.

| Логін | Пароль | Роль |

<summary><code>POST /api/auth/register/</code> — реєстрація</summary>

**Доступ:** усі. **Заголовки:** `Content-Type: application/json`.

**Request body:**

```json
{
  "username": "olena_koval",
  "first_name": "Олена",
  "last_name": "Коваль",
  "email": "olena.koval@ukma.edu.ua",
  "password": "Mohyla2026pass",
  "password_confirm": "Mohyla2026pass"
}
```

| Поле | Обов'язкове | Обмеження |
|---|:---:|---|
| `username` | так | до 150 символів; літери, цифри та `@ . + - _`; унікальне |
| `first_name` | ні | до 150 символів, можна не передавати або передати `""` |
| `last_name` | ні | до 150 символів, можна не передавати або передати `""` |
| `email` | так | коректний формат (`name@example.com`), до 254 символів, унікальний |
| `password` | так | від 8 до 128 символів; не схожий на username чи email, не з переліку поширених паролів, не лише з цифр |
| `password_confirm` | так | до 128 символів, має збігатися з `password` |

**Responses:**

`201 Created` — створений користувач (пароль у відповіді не повертається):

```json
{
  "id": 107,
  "username": "olena_koval",
  "first_name": "Олена",
  "last_name": "Коваль",
  "email": "olena.koval@ukma.edu.ua"
}
```

`400 Bad Request` — не заповнені обов'язкові поля:

```json
{
  "username": ["Це поле обов'язкове."],
  "email": ["Це поле обов'язкове."],
  "password": ["Це поле обов'язкове."],
  "password_confirm": ["Це поле обов'язкове."]
}
```

`400 Bad Request` — некоректний email і закороткий пароль:

```json
{
  "email": ["Введіть коректну адресу електронної пошти."],
  "password": ["Переконайтесь, що в цьому полі мінімум 8 символів."]
}
```

`400 Bad Request` — паролі не збігаються, пароль слабкий (`"password": "12345678"`):

```json
{
  "password_confirm": ["Паролі не збігаються."],
  "password": [
    "Пароль занадто поширений.",
    "Цей пароль повністю складається із цифр."
  ]
}
```

`400 Bad Request` — username або email уже зайняті:

```json
{
  "username": ["Користувач з таким ім'ям вже існує."],
  "email": ["Користувач з таким email вже існує."]
}
```

</details>

<details>
<summary><code>POST /api/auth/login/</code> — вхід, отримання токенів</summary>

**Доступ:** усі. **Заголовки:** `Content-Type: application/json`.

**Request body:**

```json
{
  "username": "olena_koval",
  "password": "Mohyla2026pass"
}
```

**Responses:**

`200 OK` (токени скорочено):

```json
{
  "refresh": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.<payload>.<signature>",
  "access": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.<payload>.<signature>"
}
```

У `payload` токена лежать `token_type` (`access` або `refresh`), `user_id`, `iat` (коли видано) та `exp` (коли закінчується). Payload не зашифрований, тому в токен не кладуть секретних даних. Підробити його не можна: підпис перевіряється за `SECRET_KEY` сервера.

`400 Bad Request` — не передано логін або пароль:

```json
{
  "username": ["Це поле обов'язкове."],
  "password": ["Це поле обов'язкове."]
}
```

`401 Unauthorized` — неправильний логін або пароль. Повідомлення свідомо не уточнює, що саме неправильне, щоб не підказувати, які логіни існують:

```json
{
  "detail": "Неправильне ім'я користувача або пароль."
}
```

</details>

### Заплановані ендпоінти

Ці ендпоінти ще не реалізовані (⏳). Вони з'являться в наступних роботах разом з профілем, кошиком і замовленнями. Тут описано, як вони працюватимуть. Усі, крім `GET /api/info/`, вимагатимуть заголовок `Authorization: Bearer <access>`.

#### Профіль користувача

<details>
<summary><code>PATCH /api/auth/me/</code> — редагування профілю</summary>

**Використання:** форма редагування профілю. Передаються лише поля, які змінюються.

**Request body:**

```json
{
  "bio": "Люблю квартирники і настолки, граю на укулеле",
  "study_year": 3
}
```

Можна змінити: `first_name`, `last_name`, `faculty`, `study_year`, `is_graduate`, `bio`. Поля факультету, курсу й «про себе» з'являться разом із профілем.

**Responses:**

`200 OK` — оновлений профіль (як у `GET /api/auth/me/`).

| Статус | Коли |
|---|---|
| `400 Bad Request` | Некоректні дані (наприклад, `study_year` не від 1 до 6 або `bio` довше за 500 символів) |
| `401 Unauthorized` | Користувач не увійшов |

## Postman-колекція

Колекція з усіма реалізованими ендпоінтами лежить у [`postman/kma-tusa.postman_collection.json`](postman/kma-tusa.postman_collection.json) (формат Collection v2.1). Для кожного ендпоінта є успішні запити і запити з помилками (`400`, `401`, `403`, `404`, `405`, `409`), до кожного збережено приклад відповіді.

| Папка | Що перевіряє |
|---|---|
| Авторизація | Реєстрація та її помилки, вхід користувача й адміністратора, неправильний пароль, оновлення `access`, `/api/auth/me/` з токеном і без |
| Права доступу | Гість читає (`200`), гість змінює (`401`), користувач змінює категорії й локації (`403`) |
| Категорії, Організатори, Локації, Тусовки | CRUD і бізнес-правила, як у попередній роботі |
| Загальні помилки | `405` і тіло запиту, що не є JSON |

**Як колекція передає токен.** Запити «Логін користувача» і «Логін адміністратора» зберігають токени у змінні колекції `user_access`, `user_refresh` та `admin_access`. Папки «Категорії» й «Локації» мають авторизацію `Bearer Token` зі значенням `{{admin_access}}`, а «Організатори», «Тусовки» й «Загальні помилки» — `{{user_access}}`. Запити всередині папок успадковують її (**Authorization → Inherit auth from parent**).

1. Запустіть сервер з демо-даними й демо-користувачами (`python manage.py loaddata demo users`, див. [Як запустити проєкт](#як-запустити-проєкт)).
2. У Postman натисніть **Import** і виберіть файл колекції.
3. Базова адреса сервера задана у змінній колекції `base_url` (`http://127.0.0.1:8000/api`). Якщо сервер працює на іншій адресі, змініть її у вкладці **Variables** колекції.
4. Запустіть усю колекцію по порядку: **Run collection**. Спершу виконується папка «Авторизація», яка отримує токени для решти запитів. Запити «Створити ...» зберігають id нового запису у змінні `new_*_id`, а реєстрація використовує `{{$timestamp}}` в імені користувача, тому колекцію можна запускати повторно.

Те саме з командного рядка через [newman](https://www.npmjs.com/package/newman) (потрібен Node.js):

```bash
npx newman run postman/kma-tusa.postman_collection.json
```

Очікуваний результат: 58 запитів, 77 перевірок, 0 помилок.

## Схема бази даних

![Схема бази даних](docs/db-schema.png)

| Таблиця | Що зберігає | Готово |
|---|---|:---:|
| `categories` | Типи тусовок (вечірка, квартирник…) | ✅ |
| `organizers` | Організатори тусовок | ✅ |
| `venues` | Локації: тип, район, адреса, місткість | ✅ |
| `events` | Тусовки: час, лайнап, дрес-код, тип входу, ціна, мінімальний донат, дані збору, місткість. Кожна має одного організатора, одну категорію та одну локацію | ✅ |
| `users` | Зареєстровані користувачі та адміністратори. Використовується вбудована модель Django `User` (таблиця `auth_user`), адміністратор має `is_staff = True` | ✅ |
| `cart_items` | Кошик: на які тусовки і скільки квитків користувач відклав | ⏳ |
| `orders` | Замовлення користувача | ⏳ |
| `order_items` | Позиції замовлення з ціною на момент оформлення | ⏳ |

У Django таблиці мають префікс застосунку: `events_event`, `events_organizer` тощо. Таблиця користувачів належить вбудованому застосунку `auth` (`auth_user`).

**Зв'язки:**

- `organizers` 1 — N `events`
- `venues` 1 — N `events`
- `categories` 1 — N `events`
- `users` 1 — N `cart_items`, `events` 1 — N `cart_items`
- `users` 1 — N `orders`
- `orders` 1 — N `order_items`, `events` 1 — N `order_items`

Зовнішні ключі з `events` мають `on_delete=PROTECT`: база не дасть видалити організатора, локацію чи категорію, поки на них посилається хоча б одна тусовка. API перевіряє це ще до видалення і повертає `409` зі зрозумілим повідомленням.

Необов'язкові текстові поля зберігаються як порожній рядок, а не `NULL`, як рекомендує документація Django.

Файл-джерело діаграми для draw.io: [`docs/db-schema.drawio`](docs/db-schema.drawio).
